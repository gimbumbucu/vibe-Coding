# TDD Workflow

## Steps

### Step 1: 요구사항 분석 및 테스트 대상 파악

사용자가 요청한 기능 또는 수정 사항을 분석합니다.

- 구현해야 할 기능이 무엇인지 명확히 정의합니다.
- 현재 코드베이스에서 관련 파일과 기존 테스트 구조를 파악합니다.
- 엣지 케이스와 경계 조건을 식별합니다.
- 테스트할 함수/클래스/모듈의 입력과 기대 출력을 정의합니다.
- 분석 결과를 사용자에게 요약하여 공유하고 확인을 받습니다.

---

### Step 2: 🔴 RED — 실패하는 테스트 작성

아직 구현되지 않은 기능에 대한 테스트를 먼저 작성합니다.

- 기존 테스트 파일이 있으면 해당 파일에 추가하고, 없으면 새로 생성합니다.
- 테스트는 구체적이고 하나의 동작만 검증해야 합니다(단일 책임 원칙).
- 테스트 이름은 `test_<동작>_<조건>_<기대결과>` 형식으로 명확하게 작성합니다.
- 다음 케이스를 포함합니다:
  - 정상 케이스 (Happy Path)
  - 경계값 테스트
  - 예외/에러 케이스
- 테스트를 실행하여 **반드시 실패(RED)** 하는 것을 확인합니다.
- 실패 이유가 "구현 없음" 때문임을 검증합니다. (컴파일 오류나 임포트 오류가 아닌지 확인)

---

### Step 3: 🟢 GREEN — 테스트를 통과하는 최소한의 구현

테스트를 통과시키는 가장 단순한 코드를 작성합니다.

- 과도한 최적화나 일반화 없이 테스트를 통과시키는 데만 집중합니다.
- 중복 코드가 있어도 괜찮습니다. 이 단계에서는 동작하는 코드가 목표입니다.
- 구현 후 테스트를 실행하여 **모든 테스트가 통과(GREEN)** 하는 것을 확인합니다.
- 기존에 통과하던 테스트가 깨지지 않았는지 전체 테스트 스위트를 실행합니다.

---

### Step 4: 🔵 REFACTOR — 코드 품질 개선

테스트가 모두 통과된 상태에서 코드를 개선합니다.

- 중복 코드를 제거하고 공통 로직을 추출합니다.
- 변수명, 함수명, 클래스명을 의미 있게 개선합니다.
- 복잡한 조건문을 단순화하거나 별도 함수로 추출합니다.
- 함수/메서드가 하나의 책임만 갖도록 분리합니다.
- 코드 스타일을 프로젝트 컨벤션에 맞게 정리합니다.
- 리팩토링 후 테스트를 다시 실행하여 **모든 테스트가 여전히 통과** 하는지 확인합니다.

---

### Step 5: 반복 여부 결정

구현해야 할 기능이 남아 있는지 확인합니다.

- 아직 커버되지 않은 케이스나 기능이 있으면 **Step 2로 돌아가** 다음 테스트를 작성합니다.
- 모든 요구사항이 구현 완료되었으면 Step 6으로 진행합니다.

---

### Step 6: 최종 검증 및 요약

전체 작업을 마무리하고 결과를 요약합니다.

- 전체 테스트 스위트를 실행하여 최종 통과 여부를 확인합니다.
- 작성된 테스트 목록과 각 테스트의 목적을 정리합니다.
- 구현된 기능의 동작 방식을 간략히 설명합니다.
- 코드 커버리지가 측정 가능하다면 확인하여 미커버 영역을 파악합니다.
- 사용자에게 결과를 보고하고 추가 개선 사항이 있는지 논의합니다.
